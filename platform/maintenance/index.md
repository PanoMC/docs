# Maintenance Mode

> ⚠️ Maintenance mode is configured in **Panel → Settings → Platform** and requires the
> **Manage Platform Settings** permission.  
> If you are not logged in as an **Admin**, you must hold that permission to see or change the **Maintenance Mode** card.

**Maintenance mode** takes your public website offline without stopping Pano. While it is on, visitors never reach your
theme — Pano serves its own self-contained maintenance page straight from the backend instead. Your admin panel, your
connected Minecraft servers, and everything you need to finish the work keep running normally.

Because that page is rendered by Pano itself, maintenance mode works with **every theme** and requires no theme support
whatsoever. You can install, switch, update or outright break your theme while it is on, and visitors still see a proper
page instead of an error.

## Features

- **One switch.** Turn the public site off and on from **Panel → Settings → Platform → Maintenance Mode**, confirming
  with your account password. It applies immediately — no restart, and your own panel session is never interrupted.
- **Theme-independent page.** The maintenance page is generated by Pano and stored as a single Handlebars file on disk,
  so it renders even when no theme is able to start.
- **Editable content.** Page title, a rich-text message (the same editor used for the registration agreement), your site
  logo, and your own CSS.
- **Permission-based bypass.** Staff who hold the right permission can log in and keep browsing the real site.
- **Skip button.** An authorized visitor sees the maintenance page with a **Skip maintenance mode** button that hands
  them the real theme.
- **Built-in login.** A deliberately minimal username/e-mail + password form served by Pano, independent of any login
  plugin.
- **Brute-force protection.** An address that goes past the failed-login limit (three attempts by default) is banned
  permanently, recorded in the panel activity log, and manageable from the panel.
- **Public APIs closed.** Public API endpoints are closed to ordinary visitors while maintenance mode is on, and work
  again for anyone who is allowed to bypass it.
- **Search-engine safe.** Pages answer `503 Service Unavailable` with `Retry-After`, which search engines read as
  "temporarily down, come back later" instead of "gone".

## Turning Maintenance Mode On

1. Go to **Panel → Settings → Platform**.
2. Scroll to the **Maintenance Mode** card.
3. Flip **Enable Maintenance Mode** in the card header and type your account password. Taking the site offline — and
   putting it back up — is re-authenticated like the other critical settings, and applies the moment the password is
   accepted. The rest of the card saves without a password.
4. Adjust the settings in the card body: who may bypass, the login button, the page content.
5. Press **Save**.

The change is live on the very next request. Maintenance mode does **not** require a restart and does **not** raise the
"restart required" notice that port or URL changes do.

While maintenance mode is on, every page of the panel shows a banner — *"Maintenance mode is on. Visitors see the
maintenance page instead of your website."* — with a **Go to settings** link. It cannot be dismissed; it disappears when
you turn maintenance mode off.

> ⚠️ Maintenance mode only applies once your installation is set up. During the initial setup wizard it stays inert,
> whatever the setting says.

## Panel Settings

Everything lives on one card in **Panel → Settings → Platform**:

- **Enable Maintenance Mode** *(header toggle)* — the master switch. Everything else on the card is greyed out and inert
  while it is off, exactly like the **SMTP** card below it.
- **Who Can Bypass** — one field: the permission node a user must hold. Leave it empty for the panel access permission,
  which is what the placeholder spells out. See [Who Can Bypass Maintenance Mode](#who-can-bypass-maintenance-mode).
- **Show Login Button** — adds a login button to the maintenance page.
- **Custom Login URL** — a path of your own that serves the maintenance login form, for example `/staff-entrance`.
  Available only while **Show Login Button** is off. It must start with `/`, contain no spaces, stay under 128
  characters, and must not point inside `/api` or `/panel/api`.
- **Show Site Logo** — displays the logo from **Panel → Settings → Website** above the title.
- **Edit Maintenance Page** — opens the source editor for the page and its blocks, with a live preview underneath. See
  [Editing the Maintenance Page](#editing-the-maintenance-page). It stays available while maintenance mode is off, so
  you can write the page before you need it.
- **Preview Maintenance Page** — opens the maintenance page in a new tab, even if you have already skipped it.
- **Banned IP Addresses** — at the bottom of the card; opens the list the maintenance login has locked out. See
  [Banned IP Addresses](#banned-ip-addresses).

Press **Save** to apply the card. The **Save** button stays disabled until you actually change something, and a toast
confirms the result. Every change takes effect on the next request — nothing here needs a restart.

## Who Can Bypass Maintenance Mode

A visitor may bypass maintenance mode only if they are **logged in** and **hold the required permission**.

The **Who Can Bypass** field on the card is the node Pano requires. It is a single field with two states:

- **Left empty** — the default. Pano requires `pano.panel.access.panel`, shown in the panel as **Access Panel** and
  written into the field's placeholder, so anyone who can already open your admin panel can also get past the
  maintenance page.
- **Filled in** — for example `admins.test`. Pano then requires that exact node instead. This lets you let in people who
  should see the site but must never see the panel.

> ⚠️ The node you type is matched **literally** and **may not contain a wildcard** — Pano refuses to save a node
> containing `*`. Wildcards work on the node a user *holds*, not on the node you *require*: a user holding `admins.test`
> would **not** match a required node of `admins.*`, while a user holding `admins.*` matches a required `admins.test`.
> Type the exact node you grant — no spaces, at most 128 characters.

A few things worth knowing:

- Users holding the `*` (full admin) node pass any required node.
- Permission changes can take up to **a minute** to take effect, because Pano caches the permission graph, and the
  maintenance gate caches its own decision for a further 30 seconds. If a new bypass user is refused, wait and retry
  before changing anything.
- Nodes imported from LuckPerms with a `pano: false` context are ignored by Pano's web permissions. Grant the bypass
  node from **Panel → Permissions** so it carries the `pano: true` context. See the
  [LuckPerms integration](../integrations/luckperms/) page.
- The permission is re-checked on the server on every single request. Revoking it takes the user's access away, whether
  or not they already pressed the skip button.

## The Login Button and the Login URL

Where the maintenance login form lives depends on two settings:

| Show Login Button | Custom Login URL | Button on the page | URL that serves the login form |
| --- | --- | --- | --- |
| On | *(ignored, field greyed out)* | Yes → `/login` | `/login` |
| Off | *(empty)* | No | `/panel` |
| Off | `/staff-entrance` | No | `/staff-entrance` — and `/panel` no longer shows the form |

Three consequences to keep in mind:

- A secret address only makes sense as the **alternative** to a visible button, so the **Custom Login URL** field is
  greyed out while the button is on. With the button on the login is simply at `/login`, and `/login` is served by
  **Pano**, not by your theme. Your theme's own login page is unreachable for as long as maintenance mode is on — that
  is intentional.
- With the button off, a custom address becomes the **only** address that serves the form. Write it down before you
  save.
- Anonymous visitors who open `/panel` — or any deep link under it, such as a bookmarked `/panel/posts` — are redirected
  to whichever address serves the login form, so a saved panel link still leads somewhere useful.

## What Visitors See

An ordinary visitor gets the maintenance page on **every** address of your site — the home page, deep links, and any
theme asset. The page shows, in order: your site logo (if enabled), the page title, your message, and — if you enabled
it — the login button. Your custom CSS is applied last, so it wins over the built-in styles.

Under the hood:

- Pages answer `503 Service Unavailable` with a `Retry-After` header and `X-Robots-Tag: noindex`. Search engines read a
  503 as *temporarily* unavailable: they pause crawling while maintenance mode is on and resume once it is off, instead
  of dropping your pages from the index the way a `404` would. None of the maintenance text gets indexed.
- The login page itself answers `200 OK` (still `noindex`), because password managers and browser form handling break
  on a 503.
- `/robots.txt` answers a plain-text 503 containing `User-agent: *` / `Disallow: /`.
- Public API endpoints answer `503` with the error code `MAINTENANCE_MODE_ENABLED`, so nothing your theme would
  normally fetch leaks out. APIs added by addons behave the same way — they are closed unless the addon explicitly opts
  out.
- Anything that is not a `GET` or `HEAD` request gets a short plain-text 503.

## What an Authorized User Sees

A logged-in user holding the required permission **also lands on the maintenance page**, but with a **Skip maintenance
mode** button. Pressing it lets them browse the real theme normally: pages render, and the API calls your theme makes
work for them again.

- **The skip lasts until you reload.** It is spent by the page it was granted for, so browsing inside the theme keeps
  working, but pressing <kbd>F5</kbd>, opening a new tab or typing a URL brings the maintenance page straight back and
  you press **Skip maintenance mode** again. That is deliberate: nobody should be able to forget the site is closed
  because they skipped it hours ago.
- The skip is carried by a `pano_maintenance_skip` cookie, which is only a statement of intent — it opens nothing by
  itself, because the permission is verified server-side on every request.
- **To go back to the maintenance page without reloading**, open `/api/maintenance/exit` — which is exactly what
  **Preview Maintenance Page** in the panel does — or simply log out. Logging out clears the skip cookie along with the
  session.
- **`/panel` and everything under it is never blocked** for a user who can access the panel — with or without pressing
  the skip button.
- API access follows the **permission**, not the cookie: a user who may bypass maintenance mode gets normal API
  responses even before pressing the skip button. The cookie decides which interface is served; the permission decides
  which APIs answer.
- If you skip while **no theme is running** — during a theme switch, for instance — Pano keeps showing the maintenance
  page with a short notice instead of an error, and hands you the theme as soon as one is active again.

## The Maintenance Login

The login form Pano serves during maintenance asks for exactly two things: **username or e-mail**, and **password**. It
is server-rendered and needs no JavaScript, so a broken hand edit of the page cannot lock you out of the only door.

> ⚠️ Login plugins are bypassed by design. Captcha, two-factor authentication, magic e-mail links and social login are
> **not** applied to the maintenance login — that includes
> [Pano Auth Guard](../../plugins/auth-guard/), [Social Login](../../plugins/social-login/) and
> [Premium Login](../../plugins/premium-login/). This is deliberate: it guarantees you can always get back in, even when
> the plugin that normally guards your login is the thing that is broken. Those plugins apply again in full as soon as
> maintenance mode is off.

Other deliberate differences from the normal login:

- **An unverified e-mail address is accepted here.** A broken mail server is a common reason to be in maintenance in the
  first place. A user who is banned from your site is still refused.
- **Nothing is leaked.** The form never distinguishes "no such user" from "wrong password"; every failure gives the same
  message.
- **The form only works from Pano's own page.** A submission coming from another site is rejected with `403` and does
  **not** count as a failed attempt — otherwise any web page could get its visitors banned from your site. If it is only
  your own form token that expired, the answer is the form again with a fresh token and a short notice, never a dead
  end.
- **Rate limited.** The maintenance login has a budget of its own — a handful of attempts every few seconds — that no
  other endpoint shares, so nobody can drain it by hammering your normal login. Going over it never bans you: you are
  sent back to the maintenance page with a "too many attempts" notice. The budget is counted per connecting address,
  exactly like the bans below, so read the reverse-proxy note there if Pano runs behind a proxy.

Where you land after a successful login:

- Panel access → the **panel**.
- Only the custom bypass node → the **maintenance page**, now with the skip button.
- Correct password but no bypass permission → the maintenance page with a "no access" notice. This is **not** counted as
  a failed attempt, so an ordinary member cannot get your office banned by trying to log in.

## Banned IP Addresses

- **Three** failed logins from the same address are tolerated; the **next** failure bans that address **permanently**,
  and from then on every attempt is refused before the password is even checked. Banned visitors get the maintenance
  page with no login form at all, just a notice telling them the address is blocked and to contact the site owner.
- A **successful** login resets that address's counter to zero, and restarting Pano forgives counters that have not
  reached the limit yet. Bans themselves survive restarts.
- The threshold is `max-login-attempts` in `config.conf` (default `3`). Setting it to `0` disables banning entirely.
- **Loopback addresses (`127.0.0.1` and `::1`) are never counted and never banned.** Someone with terminal access to the
  machine Pano runs on can always log in.
- Every automatic ban is written to the panel activity log, together with the ban-removal and on/off events.

Bans are stored on disk, in the folder Pano runs from:

```
maintenance/maintenance-mode-banned-ips.json
```

```json
{
  "version": 1,
  "bans": [
    {
      "ip": "203.0.113.44",
      "bannedAt": 1753612800000,
      "attempts": 4,
      "lastUsernameTried": "admin",
      "lastUserAgent": "Mozilla/5.0 (X11; Linux x86_64)",
      "socketPeer": "203.0.113.44"
    }
  ]
}
```

To manage them, press **Banned IP Addresses** at the bottom of the **Maintenance Mode** card; the list opens in its own
window. It shows the **IP**, the **Connection Address** the request actually came from, the number of **Failed
Attempts**, the **Last Username Tried** and the ban date. You can **Remove ban** for one address or press **Clear All**.
Removing a ban also clears that address's failure counter. The list stays reachable while maintenance mode is off —
bans outlive it.

The list is capped at 10 000 entries, and a damaged ban file never locks anyone out: Pano backs it up as
`maintenance-mode-banned-ips.json.corrupt-<timestamp>` and starts again with an empty list.

> ⚠️ **Behind a reverse proxy or CDN?** Pano identifies a maintenance-login client by the address of the connection it
> actually receives. `X-Forwarded-For` is ignored **entirely** unless that connecting address is listed in
> `server.trusted-proxies` — and the same identity governs both this ban list and the maintenance login's rate limit. If
> you run Pano behind Nginx, Cloudflare or any other proxy and do not fill that list in, **every** request looks like it
> comes from the proxy: failed logins by anyone would ban that single address, and with it everyone's access to the
> maintenance login. Add your proxy there — and only your proxy, since a listed address is trusted to name the real
> client. See the [Cloudflare guide](../advanced/cloudflare/).

This list is separate from the site-wide banned-IP feature; it only governs the maintenance login.

## Editing the Maintenance Page

**Edit Maintenance Page** on the card opens a source editor: the markup on the left, a live preview of the real page
underneath it, and one tab per editable block.

| Tab | File | What it is |
| --- | --- | --- |
| **Page** | `maintenance/page.hbs` | The whole document — head, styles, layout. The blocks below drop into its slots. |
| **Login form** | `maintenance/login.hbs` | The username/password form served on the login URL. |
| **Login button** | `maintenance/login-button.hbs` | The button that points visitors at the login page. |
| **Skip button** | `maintenance/skip.hbs` | The **Skip maintenance mode** button authorized visitors see. |
| **Notice** | `maintenance/notice.hbs` | The banner that carries errors and status messages. |

The preview always renders **every** block at once, whichever tab you are on, so you can see the whole interface you are
styling. A live request only ever shows the blocks that apply to it.

All five files live in the folder Pano runs from and are plain Handlebars templates. There is no rich-text editor: you
write the markup.

### What saving changes

Pressing **Save** writes the files and sets `custom-page = true`. From that moment:

- Pano no longer composes the page from `title`, `message-html` and `custom-css` in `config.conf`.
- A Pano update that ships a new default design **no longer replaces your files** — the improvement will not reach you
  until you reset.

**Reset to default** restores all five files from the design Pano ships and turns `custom-page` back off, which also
re-enables future design updates. `custom-page = false` in `config.conf` does the same thing.

### Slots and variables

::: v-pre

The page carries these; leave one out and the feature it brings simply does not appear — a page with no
`{{{loginBlock}}}` never shows a login button, and one with no `{{{skipBlock}}}` leaves authorized visitors no way to
reach the site.

| Slot | What it becomes |
| --- | --- |
| `{{{noticeBlock}}}` | The notice banner, when there is one |
| `{{{loginBlock}}}` | The login button, or the login form on a login URL |
| `{{{skipBlock}}}` | The **Skip maintenance mode** button, for authorized visitors |
| `{{{creditBlock}}}` | The **Created with Pano** line |
| `{{logoUrl}}` | The site logo URL |
| `{{lang}}` | The platform language code, for `<html lang>` |
| `{{defaultTitle}}` / `{{{defaultMessage}}}` | Pano's own copy, in the platform language |

The blocks get their own variables: the login form has `{{action}}`, `{{nonce}}`, `{{nonceField}}`, `{{usernameField}}`,
`{{passwordField}}` and the labels and placeholders around them; the login button has `{{url}}` and `{{label}}`; the skip
block has `{{action}}`, `{{label}}` and `{{description}}`; the notice has `{{text}}`, `{{modifier}}` and `{{role}}`.
**Keep `{{nonce}}` and `{{nonceField}}` in the login form** — they carry the same-origin check that stops another site
from getting your visitors' addresses banned.

:::

Every label, button and message comes from Pano's own translations and follows
**Panel → Settings → Platform → Preferences → Language**. You can rewrite any of those strings in
**Panel → Translations** under the **PLATFORM** type; the maintenance keys are grouped under `maintenance.`.

A broken directive shows up in the preview rather than on the live site, because the preview renders through the same
engine. If a block fails to render, the page still comes up without it; if the page itself cannot be read at all, Pano
falls back to a minimal built-in page, so the site is never left without an answer.

### Notes on the default design

- The files are self-contained on purpose: no theme assets, no external stylesheets, no scripts from your site. That is
  what lets the page render while your theme is down.
- The default design is flat, quiet and **always light** — it does not follow the visitor's dark-mode setting, so the
  page looks the same for everyone. It carries the same **Created with Pano** line the themes show in their footer.
- `title`, `message-html` and `custom-css` in `config.conf` are what Pano composes the *default* page from. They are not
  editable from the panel any more: once you are in the editor, the markup itself is the thing you edit.

You can point the folder somewhere else at launch, the same way as the other Pano folders:

```bash
java -Dpano.maintenanceFolder=/var/lib/pano/maintenance -jar Pano-<version>.jar
```

## What Keeps Working During Maintenance

Maintenance mode closes the public website, not the platform. These keep working, always:

- **The admin panel** and every panel API — for users who can access the panel.
- **The Pano MC Plugin connection.** Your Minecraft servers stay connected, player data keeps syncing, and in-game
  integrations such as [AuthMeReloaded](../integrations/authme/) and [LuckPerms](../integrations/luckperms/) are
  unaffected.
- **The health endpoint** `/api/health`, so uptime monitors and load balancers keep getting a normal answer.
- **The maintenance page and its login**, plus the site info, logo, favicon and interface translations they need.
- **Let's Encrypt certificate renewal** (`/.well-known/acme-challenge/`), so SSL does not expire while you work. That
  challenge path is the only exemption: anything else under `/.well-known/` gets the maintenance page like any other
  address.

Everything else — your theme, its assets, the public API, and any API added by an addon — is closed to ordinary
visitors, and open again to a user who may bypass maintenance mode.

> ⚠️ Maintenance mode is a **switch, not a security boundary.** Already-authenticated Minecraft servers and everyone
> with the bypass permission keep working by design. Use it to hide a half-finished site, not to contain an incident.

## Configuration Keys

Maintenance mode is stored in `config.conf`. Pano adds the block automatically on first start after the update; you
normally manage it from the panel and only touch the file to recover.

```jsonc
maintenance {
  # Master switch. When enabled, normal visitors get the maintenance page instead of the theme
  # and every public API endpoint returns 503.
  enabled = false

  # Permission node required to bypass maintenance mode.
  # Empty = the panel access permission (pano.panel.access.panel).
  # Wildcards are NOT allowed here: the node is matched as a literal target.
  bypass-permission-node = ""

  # Show a "Log in" button on the maintenance page.
  show-login-button = true

  # Path that serves the maintenance login form, e.g. "/staff-entrance".
  # Empty = /login when show-login-button is true, otherwise /panel.
  custom-login-url = ""

  # Show the website logo at the top of the maintenance page.
  show-site-logo = true

  # Maintenance page title (also the browser tab title). Empty = built-in default.
  title = ""

  # Maintenance page body (HTML, edited with the rich-text editor in the panel).
  message-html = ""

  # Extra CSS injected into the maintenance page <style> block.
  custom-css = ""

  # Wrong-password attempts from one IP before that IP is permanently banned from the
  # maintenance login. 0 disables IP banning. Loopback addresses are never banned.
  max-login-attempts = 3

  # True once the whole page has been written from the panel's full-page editor.
  # maintenance/page.hbs then owns the page: the fields above stop driving it and a new
  # default design shipped with an update no longer replaces it.
  custom-page = false
}
```

**Details**

- `enabled`: the only key you need to touch to recover from a lockout.
- `bypass-permission-node`: an exact node, e.g. `admins.test`. Leave empty for the default.
- `show-login-button` / `custom-login-url`: see the table in
  [The Login Button and the Login URL](#the-login-button-and-the-login-url).
- `title`, `message-html`, `custom-css`, `show-site-logo`: the source of truth for the page content.
  `maintenance/page.hbs` is re-rendered from them on every save, so hand-edits to that file are overwritten the next
  time the panel saves.
- `max-login-attempts`: not shown in the panel — this key is the only place to change it.
- Editing this block by hand is picked up **within a few seconds without a restart**. Saving from the panel rewrites the
  whole file, so a panel save and a hand edit made at the same time will overwrite each other.

One key in the `server` block belongs to the same story:

```jsonc
server {
  # Reverse proxies allowed to declare the real client IP via X-Forwarded-For.
  # The header is honoured ONLY when the connecting socket peer is listed here;
  # otherwise the socket peer address itself is used as the client IP.
  # An empty list means every connection is treated as direct — no header is trusted.
  # Example: ["127.0.0.1", "::1"]
  trusted-proxies = []
}
```

- `trusted-proxies`: the addresses whose `X-Forwarded-For` header Pano believes. The list is **empty by default**, so
  every request is treated as a direct connection and the header is ignored entirely — the safe default, but the wrong
  one for a site behind a proxy. Fill it in with your proxy's address, and nothing else, before you rely on maintenance
  mode in production. It is currently read by maintenance mode only, for the maintenance login's IP bans and its rate
  limit; the rate limiting of every other endpoint is unaffected by this key.

## Locked Yourself Out?

Maintenance mode is designed so you can always get back in. In order of preference:

1. **Log in from the machine Pano runs on.** Loopback addresses (`127.0.0.1`, `::1`) are never banned, so a browser or
   an SSH tunnel on the server itself always reaches the login form.
2. **Turn it off in `config.conf`.** Set `enabled = false` in the `maintenance` block and save. Pano picks the change up
   within about five seconds — no restart needed. This is also the route to take if the panel switch is refusing your
   password: the file needs no re-authentication.
3. **Clear the banned addresses.** Remove them from the panel, or delete
   `maintenance/maintenance-mode-banned-ips.json`. Pano recreates it empty.
4. **Reset the page.** If a bad custom CSS or a broken hand edit made the page unusable, delete `maintenance/page.hbs`
   and Pano regenerates it from the default template.
5. **Forgot the custom login URL?** Read `custom-login-url` from the `maintenance` block in `config.conf`, or clear it —
   the form then goes back to `/login` or `/panel`, depending on `show-login-button`.
6. **Locked out by the permission node?** Clear `bypass-permission-node` to fall back to the panel-access permission.

> ⚠️ Always take a backup before large manual edits to `config.conf`, and stop Pano first if you are changing more than
> a single value. See the [Configuration Guide](../configuration/).

## Required Permissions

- **Manage Platform Settings** (`pano.panel.manage.platform.settings`) — configure maintenance mode and manage the
  banned-IP list.
- **Access Panel** (`pano.panel.access.panel`) — the default permission required to bypass maintenance mode, unless you
  set a custom node.

> Turn it on before the work starts, not after something breaks — see the
> [production checklist](../configuration/production/).
