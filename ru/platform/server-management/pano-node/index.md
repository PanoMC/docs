# Демон pano-node

`pano-node` — небольшой демон, который устанавливает **управляемые** серверы Minecraft на машине и
следит за ними. Именно он превращает машину в [узел](../#узлы): Pano говорит ему, что установить,
когда запустить и остановить сервер и что записать в `server.properties`, а он сообщает обратно
состояние, вывод консоли и метрики.

> ⚠️ Демон выходит сначала в канале **alpha**, вместе с тем выпуском Pano, которому он принадлежит.
> Затем обычным порядком он доходит до `beta` и стабильного выпуска — так что в стабильной установке
> его может ещё не быть.

Это всегда **отдельный процесс**, никогда не часть собственной JVM Pano. В этом и смысл: обновление
или перезапуск Pano не должны уводить в офлайн серверы Minecraft, которыми она управляет. На машине,
где работает сама Pano, демон распаковывает из своего jar, запускает и поддерживает она — см.
[локальный узел](../#локальныи-узел). Всё, что описано на этой странице, — для случаев, когда вы
запускаете его сами: вторая машина, контейнер или хост, вместе с которым демон должен стартовать, —
а также для [Pano Agent](#the-pano-agent), того же jar, запущенного из папки одного сервера.

## Где его взять

**У своей собственной Pano** — этот источник и стоит предпочесть. Запущенная Pano отдаёт ровно того
демона, с которым она вышла, так что полученный jar по построению говорит на том же протоколе, что и
она, и для этого ничему за пределами вашей сети не обязательно быть доступным:

```bash
curl -fsSL https://panel.example.com/api/node/pano-node.jar -o pano-node.jar
curl -fsSL https://panel.example.com/api/node/pano-node.jar.sha256 | sha256sum -c -
```

Оба адреса публичны и не требуют аутентификации: jar — опубликованный артефакт, а не секрет, и сам
по себе не даёт ничего — машине, которая его скачала, всё равно придётся сопрячься, прежде чем Pano
станет с ней разговаривать. Контрольная сумма отдаётся в формате `sha256sum`, так что проверить её
можно ровно так, как выше. Оттуда же берёт jar и [скрипт установки](../#удаленные-узлы). Pano, у
которой нет jar демона на диске, отвечает на оба адреса **404**, и тогда установщик откатывается к
выпуску ниже.

**Из выпуска на GitHub** — запасной вариант. `pano-node.jar` публикуется с каждым выпуском Pano
рядом с jar платформы, вместе с `pano-node.jar.sha256` для проверки. **Берите jar из того выпуска,
который запущен у вас**: демон и платформа выходят вместе, поэтому протокол между ними всегда
совпадает.

Самому ему нужна среда **Java 17 или новее**. Это строже, чем у Pano, которая по-прежнему работает
на Java 11+, и с Java 11 демон умирает с `UnsupportedClassVersionError` при каждом запуске. На какой
Java работают *игровые серверы* — вопрос отдельный, см.
[На какой Java работает сервер](../#на-какои-java-работает-сервер).

**`git` ставить не нужно.** Установка сервера [Spigot](../#spigot-собирается-на-узле) собирает
его здесь же, через BuildTools, которая запускает `git`: если git есть в `PATH`, используется он,
а если нет — узел скачивает переносной git только для этой сборки, см.
[Git для BuildTools](#git-for-buildtools). Больше ничего в работе демона git не касается.

Это делается один раз на машину. Уже установленный узел обновляют иначе — из панели, см.
[Обновление демона](#обновление-демона).

## Запуск

```bash
# Сопряжение с Pano. Код берётся в Панель -> Серверы -> Узлы -> Добавить узел -> Вручную
# и меняется каждые 30 секунд.
java -jar pano-node.jar --pano https://panel.example.com --code 123456 --data ./node-data

# Каждый следующий запуск: сопряжение лежит в <каталог-данных>/config.conf.
java -jar pano-node.jar --data ./node-data

# Записать служебный файл для этой машины и выйти.
java -jar pano-node.jar --data ./node-data --service install
```

Сопряжение происходит один раз. Дальше у узла есть собственный токен, и он сам переподключается, с
растущей паузой, когда пропадает Pano или сеть.

### Флаги

| Флаг | |
| --- | --- |
| `--pano <url>` | Базовый адрес Pano, которой принадлежит узел, например `https://panel.example.com`. Также `--platform`. |
| `--code <код>` | Шестизначный код сопряжения из панели. Также `--pair`, `--pairing-code`. |
| `--bootstrap-token <токен>` | Одноразовый токен, который Pano выпускает, когда запускает узел на собственной машине. Руками его не вводят. |
| `--data <каталог>` | Каталог данных. По умолчанию `./node-data`, приводится к абсолютному пути. |
| `--name <имя>` | Как этот узел называется в панели. |
| `--runtime <PROCESS\|DOCKER>` | Как запускаются серверы: каждый обычным процессом (по умолчанию) или каждый в собственном контейнере Docker. См. [Запуск серверов в контейнерах](#запуск-серверов-в-контеинерах). |
| `--port-range <начало-конец>` | Порты, которые могут занимать серверы этого узла, например `25660-25669` (по умолчанию `25565-25600`; один порт записывается как `25565-25565`). Записывается в `node.port-range` в `config.conf`, так что следующие запуски его сохраняют, и сообщается Pano, который выдаёт новым серверам на этом узле порт внутри диапазона. Всё, кроме двух портов из 1–65535 в правильном порядке, отвергается при запуске. В контейнере диапазон должен совпадать с опубликованными портами. |
| `--service install` | Записать служебный файл для этой машины и выйти. |
| `--service uninstall` | Удалить этот файл и выйти. |
| `--help`, `-h` | Вывести справку. |

### Переменные окружения

У каждого флага есть эквивалент в окружении: контейнер получает всю свою настройку из переменных, и
дать ему командную строку, не пересобирая образ, нельзя. **Флаг важнее соответствующей переменной.**

| Переменная | То же, что |
| --- | --- |
| `PANO_URL` | `--pano` |
| `PANO_PAIR_CODE` | `--code` |
| `PANO_BOOTSTRAP_TOKEN` | `--bootstrap-token` |
| `PANO_NODE_DATA` | `--data` |
| `PANO_NODE_NAME` | `--name` |
| `PANO_NODE_RUNTIME` | `--runtime` |
| `PANO_NODE_PORT_RANGE` | `--port-range` (`начало-конец`, напр. `25660-25669`; пустое значение считается незаданным) |
| `PANO_NODE_JAVA_AUTO_DOWNLOAD` | `node.java-auto-download` в `config.conf` (`true` / `false`) |
| `PANO_NODE_TOOL_AUTO_DOWNLOAD` | `node.tool-auto-download` в `config.conf` (`true` / `false`) |

## Pano Agent {#the-pano-agent}

Pano Agent подключает к Pano сервер, который у вас уже работает, **прямо там, где он лежит**. Это тот
же самый демон, только отдаётся он под вторым именем — `pano-agent.jar`: вы кладёте его **в папку
сервера и запускаете вместо jar сервера**. Он запускает сервер отдельным процессом, показывает консоль
сервера в терминале так, будто вы запустили jar сервера сами, а остальное отдаёт Pano: кнопки питания,
консоль, файлы, резервные копии и расписания работают из той папки, где сервер уже лежит. Ничего не
копируется и не перемещается, а агент никогда не показывается в панели как узел — виден только
сервер.

Как и любому узлу, ему нужна **Java 17 или новее**. Сам сервер по-прежнему работает на той Java,
которая нужна его версии Minecraft, — см. [Среды Java](#java-runtimes).

### Подключение сервера

**Панель → Серверы → Добавить сервер → Подключить через Pano Agent** показывает три коротких шага:
кнопку **Скачать** для `pano-agent.jar`, команду, которая его запускает, — адрес вашей Pano и код
сопряжения в ней уже подставлены, — и индикатор ожидания, который превращается в кнопку **Открыть
сервер**, как только сервер появится. Из командной строки на этой машине:

```bash
cd /home/mc/survival        # папка сервера

# 1. Положите в неё агента: кнопкой «Скачать» в окне, по FTP, через файловый менеджер или
curl -fLo pano-agent.jar 'https://panel.example.com/api/node/pano-agent.jar'

# 2. Остановите сервер и один раз запустите агента командой из окна.
java -jar pano-agent.jar --pano 'https://panel.example.com' --code k7m2x9qa4tj3n8wp

# 3. Каждый следующий запуск.
java -jar pano-agent.jar
```

В Windows шаг 1 — это `Invoke-WebRequest -Uri '<тот же адрес>' -OutFile pano-agent.jar`; остальное
так же.

- **`pano-agent.jar` — это jar демона под другим именем.** `/api/node/pano-agent.jar` отдаёт те же
  байты, что и `/api/node/pano-node.jar`, с `.sha256` рядом и — как [демон](#где-его-взять) — без
  входа в аккаунт. Значение имеет имя: jar, имя которого начинается с `pano-agent`, работает как
  агент.
- **Код** — случайный ключ из 16 символов (его вставляют, а не набирают, поэтому он может быть
  достаточно длинным, чтобы его нельзя было угадать); он действует **1 минуту** и срабатывает
  **один раз**. Окно показывает новый код каждую минуту, так что команда в нём всегда содержит
  действующий код: копируйте её прямо перед запуском. Агент, сопряжённый по этому коду, принимается
  сразу — одобрять ничего не нужно. Если код истёк раньше, чем агент его использовал, агент сообщит
  об этом и попросит текущий.
- **Первый запуск** выполняет сопряжение, спрашивает, как запускать сервер ([ниже](#agent-first-run)),
  и подключает сервер на месте. Pano не примет папку, в которой сервер ещё работает: два процесса на
  одном мире портят его, поэтому сервер и нужно сначала остановить. Как только сервер подключён, агент
  сразу же запускает его, подсказывает, что дальше сервер запускается командой
  `java -jar pano-agent.jar`, и выводит команду, которая делает из него службу, а в окне панели
  появляется кнопка **Открыть сервер**.

### Первый запуск {#agent-first-run}

Пока агент не сопряжён, он спрашивает то, чего ему не хватает, по одному вопросу в строке. **Enter
оставляет значение в `[квадратных скобках]`.** Просто `java -jar pano-agent.jar`, без всего
остального, спрашивает обо всём (вопросы агента — на английском):

```text
$ java -jar pano-agent.jar
Pano Agent — linking /home/mc/survival to Pano. Press Enter to keep a [default].
Found start.sh — using its settings as defaults.
Pano address (your website, e.g. https://example.com): https://panel.example.com
Server jar [paper.jar]:
Memory for the server [4G]:
Extra Java arguments [-XX:+UseG1GC -XX:+ParallelRefProcEnabled]:

  Pano address:    https://panel.example.com
  Server folder:   /home/mc/survival
  Server jar:      paper.jar
  Memory:          4G
  Java arguments:  -XX:+UseG1GC -XX:+ParallelRefProcEnabled

Link this folder to Pano? [Y/n]
Pairing code (Pano panel → Add Server → Link with the Pano Agent): k7m2x9qa4tj3n8wp
```

Код сопряжения спрашивается последним, прямо перед сопряжением, чтобы код, живущий всего минуту,
был ещё свежим. Команда из окна отвечает на адрес и код через `--pano` и `--code`, поэтому в
терминале агент спрашивает только о том, как запускать сервер.

- **Pano address** (адрес Pano): адрес вашего сайта, как в браузере. Если `https://` не указан, он
  добавляется, а `/panel` в конце отбрасывается. Агент проверяет, что по этому адресу отвечает Pano;
  если нет, он объясняет почему — адрес недоступен, это не Pano или Pano слишком старая для агентов —
  и спрашивает снова.
- **Server jar** (jar сервера): jar-файлы из папки, но никогда не собственный jar агента. Если их
  несколько, они выводятся с номерами; ответьте номером или именем.
- **Memory for the server** (память сервера): `4G`, `4096M` или просто `4096` (в мегабайтах), не
  меньше 512 МБ.
- **Extra Java arguments** (дополнительные аргументы Java): пишутся как в командной строке, вместе с
  кавычками; `-` очищает значение по умолчанию. `-Xms`, `-Xmx` и `-jar` отбрасываются с пояснением:
  для памяти и jar есть свои вопросы.
- **Link this folder to Pano?** (подключить эту папку к Pano?) Enter подключает. `n` проходит по
  вопросам заново, подставляя ваши ответы как значения по умолчанию. `q` на любом вопросе или Ctrl+D
  завершает работу, ничего не записав.
- **Pairing code** (код сопряжения): то, что стоит после `--code` в команде из окна; окно
  показывает новый код каждую минуту. Если Pano его не принимает — код уже использован или истёк, —
  агент сообщает об этом и вместо выхода просит текущий.

**Значения из скрипта запуска.** Прежде чем спрашивать, агент ищет в папке `start.sh`, `run.sh`,
`start.command`, `start.bat`, `run.bat` или `start.cmd` и читает первую строку, которая запускает
`java … -jar`: её jar, её `-Xmx` и остальные флаги Java становятся значениями по умолчанию, а агент
пишет `Found start.sh — using its settings as defaults.` Папку, в которой уже был рабочий скрипт,
обычно удаётся подключить одними нажатиями Enter. Строку, в которой агент не может разобраться, он
пропускает. Память по умолчанию берётся по порядку: `-Xmx`, переданный самому агенту
(`java -Xmx4G -jar pano-agent.jar`), значение из скрипта или 2G.

**Изменить позже.** Ответы сохраняются в `.pano-agent/launch.json` для справки и используются один
раз, когда сервер подключается. Дальше память и аргументы Java сервера принадлежат Pano: меняйте их
в [параметрах запуска](../#параметры-запуска) сервера, а не в этом файле.

#### Без терминала {#agent-without-a-terminal}

- **Панели хостинга** вроде Pterodactyl передают агенту свою веб-консоль. Укажите `pano-agent.jar`
  как jar сервера и запустите сервер: вопросы появятся в консоли по одному в строке, а ответы вы
  вводите в поле команд консоли.
- **Однострочная форма** — команда из окна,
  `java -jar pano-agent.jar --pano '<адрес>' --code <код>`, — не требует отвечать на вопросы об
  адресе и коде, а остальные задаёт только в настоящем терминале. Везде ещё — в скрипте или в команде
  запуска панели — агент подключает сервер со значениями по умолчанию: найденный jar, настройки из
  скрипта запуска, а без скрипта 2G. `PANO_URL` и `PANO_PAIR_CODE` работают так же, как эти два
  флага, — для панели, где можно задать переменные окружения, но не команду.
- **Совсем без вопросов**: `--no-input` или `PANO_AGENT_NO_INPUT=true` отключает их, как и закрытый
  ввод — служба или `< /dev/null`. С адресом и кодом агент подключает сервер со значениями по
  умолчанию; без них он выводит, как подключиться. В обоих случаях запуск, который не смог
  выполнить сопряжение, завершается с кодом **77**, после которого записанный агентом служебный файл
  его не перезапускает.
- **После сопряжения агент ничего не спрашивает**: `java -jar pano-agent.jar` просто запускает
  сервер.

### Запуск в дальнейшем

`java -jar pano-agent.jar` ставится везде, где раньше запускался jar сервера, и запускает сервер
вместе с собой — если только в [параметрах запуска](../#параметры-запуска) сервера не выключено
*Запускать вместе с Pano*.

- **Скрипт запуска** (`start.sh`, `start.bat`): замените jar сервера на `pano-agent.jar`. При первом
  запуске `-Xmx` из этой строки предлагается как память сервера; дальше параметры в ней относятся к
  агенту, а не к игре: память и аргументы JVM сервера задаются в его **параметрах запуска** в Pano.
- **screen или tmux**: как раньше, `screen -S survival java -jar pano-agent.jar`. Подключитесь к
  сессии, чтобы видеть консоль и вводить команды.
- **Служба**: выполните в папке `java -jar pano-agent.jar --service install`. Команда запишет
  служебный файл для этой папки — его имя состоит из `pano-agent-` и короткого идентификатора,
  вычисленного из пути к папке, так что несколько серверов на одной машине не конфликтуют, — который
  запускает агента там от имени текущего пользователя и перезапускает его после сбоя. Как и
  [у узла](#служебные-фаилы), файл только записывается; команда, которая его включает, выводится,
  чтобы вы выполнили её сами.
- **Панель хостинга**: укажите `pano-agent.jar` как jar, с которым запускается сервер, — часто это
  настройка *Server Jar File*. Первый запуск задаёт свои вопросы в веб-консоли панели
  ([без терминала](#agent-without-a-terminal)). Если консоль не умеет отправлять ввод, добавьте
  `--pano` и `--code` в команду запуска, если панель позволяет её менять, или задайте `PANO_URL` и
  `PANO_PAIR_CODE`, если она позволяет задавать переменные окружения. После сопряжения агент игнорирует и то и другое, так что их можно
  оставить на месте.

Строки, которые вы вводите в терминале агента, уходят на сервер так же, как команды из консоли Pano, и
попадают в её историю; пока сервер остановлен, агент вместо этого сообщает об этом. Сам агент
немногословен: его собственные строки — сопряжение, подключение, подключение сервера, обновление,
отказ — а также предупреждения и ошибки помечены `[Pano Agent]`, а всё остальное пишется в
`.pano-agent/agent.log`.

### stop, Ctrl+C и «Остановить» в Pano

| Что вы делаете | Что происходит |
| --- | --- |
| Вводите `stop` в терминале агента — или нажимаете **Stop** в панели хостинга, которая вводит его за вас | **Останавливается только сервер.** Агент продолжает работать, и Pano по-прежнему управляет сервером; запустите его снова из Pano. |
| Нажимаете **Остановить** в Pano или вводите `stop` в консоли Pano | То же самое: сервер останавливается, агент ждёт. |
| Нажимаете Ctrl+C, или `systemctl stop`, `docker stop` либо панель хостинга присылают SIGTERM | Агент корректно останавливает сервер — той же остановкой, что и Pano, с её тайм-аутом, — и затем завершается сам. |

**Оба процесса завершает только остановка самого агента.** Так задумано: ввод `stop` никогда не
должен отрезать сервер от Pano.

Падение обрабатывается как на любом узле — действует *Перезапускать после падения*, — и агент в любом
случае продолжает работать.

### Где лежат его файлы

```
survival/                  папка сервера
├── pano-agent.jar
├── server.json            запись Pano о сервере
├── .pano-node/            process.json, пока сервер работает
└── .pano-agent/           собственные данные агента
    ├── config.conf        его сопряжение: токен и ключи
    ├── agent.log          его журнал
    ├── java/              среды Java, скачанные им для сервера
    ├── backups/           резервные копии сервера
    ├── updates/           подготовленное обновление агента
    └── cache/
```

- `.pano-agent/` для агента — то же, что [каталог данных](#каталог-данных) для узла, и лежит он
  внутри папки сервера: переносите папку — вместе с ней переедет и агент. `server.json` и
  `.pano-node/` — это то, что [любой узел пишет в каталог сервера](#что-он-пишет-в-каталог-сервера).
- **Панель туда не заходит.** Файловый менеджер не видит и не меняет `.pano-agent/` и `.pano-node/`,
  резервные копии не включают ни то ни другое, как и jar агента, а восстановление никогда туда не
  пишет.
- `config.conf` хранит токен агента — обращайтесь с ним как [с токеном узла](#config-conf).
  **Копируете папку сервера, чтобы сделать новый сервер?** Не копируйте `.pano-agent/` и подключите
  копию по собственному коду: два агента с одним токеном для Pano — один и тот же узел.

### Обновления

Агент обновляется сам, как любой узел: как только у Pano появляется более новый — если не выключен
[`node-auto-update`](../../configuration/#управляемые-серверы-managed-servers), — а иначе вручную в
**Панель → Настройки → Обновления**.

То, что вы запускаете, — это небольшой **лаунчер**. Часть, которая общается с Pano, работает под ним
вторым процессом, а сервер — третьим. Обновление скачивает и проверяет новый jar, записывает его
поверх `pano-agent.jar` и перезапускает на новой версии только этот средний процесс: **сервер
продолжает работать**, никого не отключает, и лаунчер — ваш терминал, сессия screen или служба — тоже
не прерывается. Если этот средний процесс когда-нибудь неожиданно остановится, лаунчер через короткую
паузу поднимет его снова. В Windows работающий jar заблокирован, поэтому новый, как и
[у узла](#linux-macos-и-windows), придётся скопировать вручную.

### Удаление

Уберите сервер из Pano. Затем

1. сервер останавливается, и из его папки убираются собственные файлы Pano — `server.json`,
   `.pano-node/` и `.pano-agent/` агента, — а миры, плагины и конфигурация остаются на месте;
2. агент сообщает, что его удалили из Pano, и штатно завершается, так что служба не запустит его
   снова;
3. `pano-agent.jar` остаётся: удалите его и снова запускайте jar сервера напрямую, как раньше.

## Запуск серверов в контейнерах

По умолчанию демон запускает каждый управляемый сервер как обычный процесс на машине. Запущенный с
`--runtime DOCKER` (или `PANO_NODE_RUNTIME=DOCKER`), он вместо этого запускает каждый из них
**в собственном контейнере Docker**.

```bash
java -jar pano-node.jar --data ./node-data --runtime DOCKER
```

- Машине нужна **команда `docker`** в `PATH` и право ею пользоваться. Демон проверяет это при
  запуске и отказывается стартовать, если Docker не отвечает, — вместо того чтобы обнаружить это на
  первом же сервере, который кто-то попробует запустить.
- **Один контейнер на сервер**, названный по нему и запущенный из официального образа
  **`eclipse-temurin`** для той версии Java, которая нужна этому серверу. Образ скачивается при
  первой необходимости.
- Память, заданная серверу, становится лимитом памяти контейнера, его игровой порт публикуется, а
  его каталог монтируется внутрь — поэтому миры, конфигурация и плагины по-прежнему лежат на машине,
  в `<каталог-данных>/servers/<uuid>/`.
- Всё, что делает панель, продолжает работать так же: консоль (ввод и вывод контейнера), кнопки
  питания, метрики процесса, файловый менеджер и резервные копии.
- **Сервер Spigot по-прежнему собирается здесь**, на машине, её JDK и её `git` (или
  [собственным git узла](#git-for-buildtools)), — внутрь контейнера
  попадает только тот jar, который выдала BuildTools. См.
  [Spigot собирается на узле](../#spigot-собирается-на-узле).

Среда запуска сообщается Pano при подключении демона, поэтому на странице «Узлы» видно, запускает ли
машина свои серверы процессами или в контейнерах. На серверы, созданные до переключения, в панели это
никак не влияет, но при следующем запуске они стартуют уже по-новому.

## Образ контейнера

Сам демон тоже может работать в контейнере — именно это разворачивает за вас установка через
**Coolify** в панели. Образ публикуется с каждым выпуском Pano как **`ghcr.io/panomc/pano-node`**, с
тегом версии (и `latest` — для стабильных выпусков).

Никакой командной строки у него нет вовсе: всё настраивается через окружение, а `/data` — это том.

```bash
docker run -d --name pano-node \
  -e PANO_URL=https://panel.example.com \
  -e PANO_PAIR_CODE=123456 \
  -e PANO_NODE_NAME=my-node \
  -e PANO_NODE_PORT_RANGE=25565-25600 \
  -v pano-node-data:/data \
  -p 25565-25600:25565-25600 \
  ghcr.io/panomc/pano-node:latest
```

- `PANO_NODE_DATA` в образе уже равна `/data`, и этот каталог объявлен томом — смонтируйте том,
  иначе всё, что узел установит, исчезнет вместе с контейнером.
- Опубликуйте **диапазон портов**, который займут серверы, и передайте узлу **тот же диапазон** в
  `PANO_NODE_PORT_RANGE`. Узел выдаёт своим серверам порты только из этого диапазона (`node.port-range`
  в его `config.conf`; `25565-25600`, если не указано иное, — это же открывает и образ) и сообщает
  его Pano, который выделяет порты внутри него. Порт, запрошенный Pano вне диапазона, переносится
  внутрь и об этом сообщается, так что сервер никогда не окажется на порту, который контейнер не
  публикует. Развёртывание через **Coolify** само задаёт `PANO_NODE_PORT_RANGE` равным
  публикуемому диапазону.
- Политика перезапуска: подготовив обновление самого себя, демон выходит с кодом **75**, поэтому
  задайте контейнеру обычный `--restart unless-stopped` (или доверьте перезапуск Coolify) — и он
  вернётся уже на новой версии.

## Каталог данных

Всё, чем владеет демон, лежит в одном каталоге — его можно смонтировать одним томом и сохранить
одной копией. За его пределы не пишется ничего.

```
node-data/
├── config.conf            сопряжение, ключи и настройки этого узла
├── pano-node.lock         замок «один демон на каталог», удерживается, пока демон работает
├── pano-node.pid          идентификатор процесса работающего демона
├── servers/<uuid>/        по каталогу на управляемый сервер: jar, миры, плагины
├── backups/<uuid>/        архивы резервных копий и их метаданные
├── cache/spigot/          собранные этим узлом jar Spigot и собственные файлы BuildTools
├── java/                  среды Java: скачанные Pano и те, что вы положили сами
├── cache/java/            архивы Java на время загрузки, удаляются после распаковки
├── tools/git/             переносной git для BuildTools на машине, где своего git нет
├── cache/tools/           архивы инструментов на время загрузки, удаляются после распаковки
├── updates/               подготовленное обновление демона, ждущее замены
├── .pano-node-retired     только после удаления узла из Pano: он больше не запустится
└── service/               служебный файл, записанный через --service install
```

Когда узел запускает сама Pano на своей машине, это `<каталог-pano>/node-data/`, а собственный вывод
демона идёт в `<каталог-pano>/logs/pano-node.log`.

**Один демон на каталог данных.** При запуске — ещё до сопряжения, чтобы проигравший демон не
зарегистрировался в Pano впустую — демон берёт блокировку операционной системы на `pano-node.lock` и
пишет рядом, в `pano-node.pid`, идентификатор своего процесса. Второй демон, направленный на тот же
каталог, находит блокировку занятой, печатает

```
Another pano-node is already running on /var/lib/pano-node (pid 4121); leaving it to it.
```

и вместо запуска выходит с кодом [76](#коды-выхода). Два демона на одном каталоге следили бы за теми
же процессами серверов и отвечали бы Pano как один и тот же узел, а к этому не готова ни одна из
сторон. Блокировку держит сам процесс, так что демон освобождает её, как бы он ни завершился; файл с
pid свеж ровно настолько, насколько свеж записавший его демон, и нужен для той самой строки в логе и
для Pano, которая читает оба файла, чтобы узнать уже работающий демон и не запускать второй.

## Что он пишет в каталог сервера

Каталог сервера принадлежит тому, кто этот сервер держит, поэтому демон пишет в него как можно
меньше и **вносит** изменения, а не создаёт файлы заново:

| | |
| --- | --- |
| `server.json` | Собственная запись узла об этом сервере: его uuid, имя, программа, версия, версия Java, память, аргументы JVM, порт, jar и переключатели запуска и перезапуска после падения. Именно благодаря ему узел после перезапуска по-прежнему знает, чем владеет. Файловому менеджеру он не виден. |
| `.pano-node/process.json` | Пишется сразу после запуска сервера и удаляется, когда этот процесс завершается под присмотром демона: идентификатор процесса, момент запуска, команда и способ запуска. Именно этот файл позволяет перезапущенному демону [подхватить сервер, который всё ещё работает](#что-переживает-перезапуск-демона). |
| `eula.txt` | Пишется, только если вы отметили Minecraft EULA в панели, а при импорте — только если файла ещё не было. |
| `server.properties` | Файл **дополняется, а не переписывается**: значения из мастера или из **Параметров запуска**, затем игровой порт и — только если их в файле не было — `motd` и `max-players`. При импорте трогается только порт. Всё остальное, что положил туда администратор или плагин, остаётся на месте. |
| Плагин Pano | Jar плагина — в `plugins/` (или `mods/`), а его `config.conf` пишется уже сопряжённым, с парой ключей RSA, созданной на узле. Путь зависит от платформы: `plugins/Pano/config.conf` в семействе Bukkit и на BungeeCord, `plugins/pano/config.conf` на Velocity, `config/pano/config.conf` на Fabric. Права «только владелец» — там, где файловая система их поддерживает. |

Сам jar плагина приходит **от Pano**, а не откуда-то, про что узлу пришлось бы знать. Если у этой
Pano есть сборка на диске — как в установке для разработки, которой через
`managed-servers.plugin-jar-dir` указали каталог, — Pano публикует этот jar по адресу
`GET /api/node/plugin-jars/<платформа>`, где платформа это `spigot`, `bungeecord`, `velocity` или
`fabric`, и отдаёт узлу именно такой путь; иначе узел отправляют прямо к свежему файлу выпуска
`PanoMC/pano-mc-plugin`. В обоих случаях узел скачивает его как любой другой артефакт и сохраняет
под тем именем, под которым его отдали.

Любой адрес, который Pano передаёт узлу для того, что **отдаёт она сама**, — включая этот —
**относительный**. Pano не знает, по какому адресу до неё добирается именно этот узел: адрес в
локальной сети за NAT, SSH-туннель на `127.0.0.1`, публичное имя — и всё это одна и та же Pano.
Точно работающий адрес ровно один — тот, по которому узел уже подключён, и узел дописывает путь к
нему. Абсолютные адреса — а это всякая сторонняя загрузка, от сборки Paper до файла с Modrinth —
проходят нетронутыми.

В `config.conf` плагина и в `server.json` узла лежат учётные данные — поэтому
[файловый менеджер](../#фаилы) отказывается их показывать и трогать.

## Импорт существующего сервера

Когда Pano просят [импортировать сервер](../#импорт-существующего-сервера), работа происходит здесь —
и всегда в **новый** каталог `<каталог-данных>/servers/<uuid>/`:

- **Из каталога на этой машине** каталог **копируется**, а не переносится: оригинал остаётся
  нетронутым, поэтому неудачный импорт ничего не стоит. Символические ссылки пропускаются, а не
  раскрываются; каталог внутри собственного каталога данных узла отклоняется — как и каталог, в
  котором нет jar сервера.
- **Из загруженного zip** архив забирается через Pano и распаковывается. Запись, которая оказалась
  бы за пределами цели, отклоняется, а единственная папка верхнего уровня внутри архива убирается,
  чтобы `my-server/server.jar` не превратился в `my-server/my-server/server.jar`.
- **Из модпака** скачивается и читается `.mrpack`: забирается каждый нужный серверной стороне файл,
  применяются сначала `overrides/` пака, затем его `server-overrides/`, и ставится тот загрузчик,
  которого пак требует, — Fabric и Quilt по их собственным сервисам метаданных, Forge и NeoForge
  запуском официального инсталлятора.

Затем узел **осматривает то, что у него получилось**, и сообщает Pano: какой jar запускаемый, на
какую программу это похоже (по манифесту jar, затем по его имени), версию Minecraft (из jar,
метаданных пака или `server.properties`), уже настроенный порт и версию Java, которая нужна этой
версии Minecraft. Именно это потом показывает панель, а то, что вы ввели в мастере, — лишь подсказка.

Порт выбирается в том же порядке: тот, который попросили вы; иначе тот, что уже стоял в
импортированном `server.properties`, если он свободен; иначе первый свободный порт из диапазона узла.

## config.conf

HOCON — как собственный `config.conf` Pano и как файл плагина Minecraft. Демон переписывает его
всякий раз, когда меняется сопряжение: атомарно, через временный файл и перемещение, и с правами
«только владелец» там, где файловая система их поддерживает.

```jsonc
platform {
  url = "https://panel.example.com"
  token = "<токен этого узла>"
  encryption-key = "<ключ AES-256, base64>"
}

node {
  name = "pano-node"
  public-key = "<открытый ключ RSA, base64>"
  private-key = "<закрытый ключ RSA, base64>"

  stop-servers-on-exit = false

  port-range {
    start = 25565
    end = 25600
  }
}
```

- `platform.token`, `platform.encryption-key` и `node.private-key` — **секреты**. Тот, у кого есть
  первые два, может выдать себя за этот узел перед вашей Pano. Обращайтесь с файлом как с закрытым
  ключом: не копируйте его между машинами, не кладите в репозиторий, не прикладывайте к обращению в
  поддержку. Если он утёк — удалите узел в панели и сопрягите машину заново, старый токен перестанет
  работать.
- **Пара RSA** создаётся один раз, при первом сопряжении, и хранится дальше. Пересоздать её —
  значит сопрягаться заново, а узел, который сопрягается при каждом старте, наплодил бы записей в
  Pano.
- `node.stop-servers-on-exit` решает, что станет с серверами Minecraft, когда остановится сам демон.
  Значение по умолчанию — **`false`** — оставляет их работать и
  [подхватывает](#что-переживает-перезапуск-демона) при следующем старте. Поставьте `true`, и демон
  на выходе остановит каждый сервер, за которым следит, как было раньше.
- `node.java-auto-download` (по умолчанию **`true`**) разрешает узлу скачивать среду Java, которая
  нужна серверу, но отсутствует на этой машине, — см. [Среды Java](#java-runtimes).
- `node.tool-auto-download` (по умолчанию **`true`**) делает то же для инструментов, нужных сборке
  Spigot, — пока это только git, — см. [Git для BuildTools](#git-for-buildtools).
- `node.port-range` — диапазон портов, которые могут занимать серверы этого узла. При подключении
  узел сообщает его Pano, и Pano выделяет порты новых серверов внутри него; порт, запрошенный Pano
  вне диапазона (введённый вручную или от Pano, который ещё не знает диапазона), как и занятый порт,
  переносится на свободный порт внутри диапазона, и об этом сообщается. Порт, который уже указан в
  собственном `server.properties` сервера, подключённого на месте, сохраняется. `--port-range` /
  `PANO_NODE_PORT_RANGE` записывают его при запуске; перепутанные местами границы в файле,
  отредактированном вручную, не отвергаются, а исправляются.
- `node.agent` и `node.agent-server` есть только у [Pano Agent](#the-pano-agent), в
  `.pano-agent/config.conf`: демон запускает этот единственный сервер на месте и отказывается
  устанавливать или импортировать любой другой. Не редактируйте их — удалите сервер в панели: это
  удалит `.pano-agent/`, а файлы сервера останутся на месте.
- Если Pano отвергает токен — например, узел удалили из панели, — демон скажет об этом и перестанет
  пытаться. Удалите `config.conf` и сопрягите машину заново со свежим кодом.

## Среды Java {#java-runtimes}

Самому демону нужна Java 17+, а **серверам**, которые он запускает, — та, что требует их версия
Minecraft: Java 8 для 1.16.4 и старше, 16 для 1.16.5, 17 до 1.20.4, 21 начиная с 1.20.5, 25 начиная
с 26.1. Узел использует среды двух видов и показывает обе на странице узла в панели
(**Серверы → Узлы → имя узла → Среды Java**):

- **Система** — найденные на машине: JVM, на которой работает сам демон, `JAVA_HOME`, `PATH` и
  обычные каталоги JDK (`/usr/lib/jvm`, `C:\Program Files\Java`, `/Library/Java/JavaVirtualMachines`,
  …). Pano ими пользуется, но никогда не обновляет и не удаляет.
- **Pano** — скачанные узлом в `<data>/java/<поставщик>-<версия>/`, например
  `<data>/java/temurin-21.0.12+1/`. В систему ничего не устанавливается, права root или
  администратора не нужны.

Если сред одной мажорной версии несколько, используется **самая новая** из них, какого бы вида она ни
была.

**Откуда берутся загрузки.** JRE [Eclipse Temurin](https://adoptium.net) через API Adoptium; где у
Temurin нет сборки этой версии для данной машины — Temurin 16 нет вовсе, нет Java 8 для Apple Silicon
и есть несколько пробелов для Windows на ARM, — узел берёт [Azul Zulu](https://www.azul.com/downloads/).
Системы на musl, например Alpine, получают сборки под musl. Каждый архив сверяется с **SHA-256**,
опубликованным поставщиком, и удаляется при несовпадении; распаковывается с проверкой путей (ничто не
может оказаться за пределами каталога среды), новая среда обязана ответить на `java -version`, и
только после этого переносится на место. Файл `.pano-managed.json` в её каталоге — то, по чему узел
узнаёт свою среду.

**Автоматическая загрузка.** Когда установке или запуску нужна Java, которой на машине нет, узел
определяет мажорную версию — закреплённую в **Параметрах запуска**, иначе минимальную для версии
Minecraft, поднятую до того, что требует сам jar, — скачивает её и продолжает. Во время установки
загрузка входит в прогресс установки; перед запуском это отдельная задача **Загрузка Java**, и сервер
всё это время остаётся в состоянии **Запускается**. Неудачная загрузка завершает запуск с причиной как
остановку — не как сбой, поэтому перезапуск после сбоя на ней не зацикливается.

Отключается это строкой `node.java-auto-download = false` в [`config.conf`](#config-conf)
(редактируйте, пока демон остановлен) или переменной `PANO_NODE_JAVA_AUTO_DOWNLOAD=false`. Тогда
запуск, которому нужна отсутствующая Java, завершается ошибкой
`No Java 21 runtime on this host; automatic Java download is disabled`, а обзор сервера предлагает
скачать её один раз.

**Из панели.** На карточке **Среды Java** есть кнопка **Установить Java**: она перечисляет версии,
которые эта машина может скачать, с поставщиком, версией, размером и назначением; версии, которые ни
один поставщик для неё не собирает, показаны бледными. У среды, установленной Pano, есть **Обновить**,
когда вышла более новая сборка этой версии, — новая ставится рядом со старой, а старая удаляется, как
только на ней ничего не работает, — и **Удалить**. Удаление запрещено, пока запущенный сервер был
стартован из этой среды или пока сервер закреплён за этой версией и это её последняя среда; кнопка
называет мешающие серверы. Системные среды из Pano удалить нельзя. Для установки и удаления нужны право
**Управление узлами** и узел в сети; узел старше этой функции показывает свои среды, но не предлагает
загрузок, пока его не [обновят](#обновление-демона).

**Машины без интернета.** Скачайте JDK или JRE сами и распакуйте в отдельный каталог внутри
`<data>/java/` (например, `<data>/java/jdk-21/` с `bin/java` внутри). Узел найдёт её при следующем
запуске и покажет как **системную** среду. Так можно с любым поставщиком и любой версией.

Остатки прерванной загрузки или удаления (`<data>/java/.tmp-*`, `<data>/java/.trash-*`, архивы в
`<data>/cache/java/`) убираются при запуске демона.

## Git для BuildTools {#git-for-buildtools}

[Spigot](../#spigot-собирается-на-узле) собирается через BuildTools. Клонирует она встроенной
библиотекой git, но для локальной работы — например, чтобы наложить патчи Spigot — всё равно
запускает `git`. Ставить его самому больше не нужно. Узел ищет git в таком порядке:

1. **git в `PATH` машины** — в приоритете, и ничего не скачивается.
2. **В Windows** больше ничего не нужно: BuildTools сама скачивает свой PortableGit (около 60 МБ на
   каждую версию Spigot) в свой рабочий каталог.
3. **В Linux и macOS** узел скачивает небольшой git (около 8 МБ, x64 и arm64), который публикуется
   вместе с выпусками Pano на GitHub как `pano-git-<os>-<arch>.tar.gz`. Архив сверяется с его
   SHA-256, распаковывается в `<data>/tools/git/<os>-<arch>-<версия>/` и должен ответить на
   `git --version`.

git узла ставится в начало `PATH` **только для процесса BuildTools** — в систему он никогда не
устанавливается, и ни ваша оболочка, ни серверы его не видят. Скачанный однажды, он используется
всеми следующими сборками, даже если загрузки выключены. Загрузка видна в ходе установки
(*Downloading git …*).

Отключается это строкой `node.tool-auto-download = false` в [`config.conf`](#config-conf)
(редактируйте, пока демон остановлен) или переменной `PANO_NODE_TOOL_AUTO_DOWNLOAD=false`. Тогда
установка Spigot на машине без git падает ещё до сборки:

```
Git is not installed on this node and automatic tool download is disabled; BuildTools needs it (apt install git / pacman -S git / brew install git).
```

Неудачная загрузка называет причину и те же пакеты. На машине без интернета поставьте git
системным менеджером пакетов.

## Версия протокола

Демон говорит на **версии протокола 2** и сообщает об этом в момент подключения — вместе со своей
версией, операционной системой, архитектурой, своими CPU, памятью и диском, найденными средами Java
и серверами, которыми уже владеет.

Он также отвечает на `CONSOLE_HISTORY` — запрос, на котором держится кнопка консоли
**Загрузить более ранние строки**: страница строк, прочитанных обратно из `logs/latest.log` этого
сервера и его ротированных архивов, с `skip`, отсчитываемым от конца журнала, и `hasMore`, который
говорит, осталось ли что-то ещё более раннее.

Узел, который говорит на более старой версии, Pano **принимает, а не отклоняет**, и просто не
предлагает того, чего та версия не умеет, — ровно та же терпимость, какую она уже проявляет к
старым плагинам Minecraft. В протоколе **2** появился запрос, на котором держится
[определение плагинов, установленных вручную](../#определение-плагинов-установленных-вручную): узлу
постарше кнопку **Определить источники** просто не показывают, потому что кнопка, единственный
возможный ответ которой — «этот узел так не умеет», хуже, чем её отсутствие.
[Обновите узел](#обновление-демона) на странице «Узлы», и она появится.

Поэтому jar и стоит брать из того выпуска Pano, который у вас запущен: они выходят вместе, так что
протокол у них всегда совпадает. Демон старше той Pano, с которой он говорит, не поймёт самых новых
сообщений — обычный признак этого — установка, которая никак не уходит из состояния «ожидание», а
лечится это обновлением jar и перезапуском демона.

## Что переживает перезапуск демона

Остановка демона **не** останавливает серверы Minecraft на этой машине. Демон, которого
перезапустили, обновили или убили, оставляет работать каждый сервер, за которым следит, — и пишет
при выходе, сколько их он оставил, — а при следующем старте забирает их обратно. Игроки остаются в
своих мирах и во время обновления узла; за те несколько секунд, пока демона нет, меняется только
одно: панели некого спросить.

Возможным это делает один маленький файл. Сразу после запуска сервера демон пишет
`<каталог сервера>/.pano-node/process.json` — идентификатор процесса, момент запуска, команду и
способ запуска (обычный процесс или имя его контейнера Docker) — и удаляет его, когда этот процесс
завершается под его собственным присмотром. При следующем старте он перечитывает эти записи и
**подхватывает** всё, что ещё живо. Записи верят только тогда, когда

- идентификатор процесса всё ещё жив,
- этот процесс стартовал именно тогда, когда говорит запись, с точностью до нескольких секунд —
  иначе операционная система уже успела отдать этот номер чему-то совсем другому,
- а его командная строка действительно принадлежит этому серверу (или, на среде Docker, контейнер
  всё ещё работает).

Запись, не прошедшую хотя бы одну из проверок, считают устаревшей: её удаляют, а сервер сообщают как
**Остановлен**. Прошедшую — сообщают Pano как работающий сервер со значком *подхвачен* в панели.

Подхваченный сервер ведёт себя как любой другой, с одним исключением: демон унаследовал процесс, но
не его **стандартный вход** — этот канал принадлежал демону, которого больше нет. Консоль всё так же
идёт — узел следит за `logs/latest.log` с текущего места и переживает ротацию, — история всё так же
листается по файлам лога, метрики продолжают приходить, а **Остановить**, **Перезапустить** и
**Убить** работают через сигналы самой операционной системы. Недоступно только писать в сервер, и
там, где у сервера есть [плагин Pano](../#подхваченные-серверы), Pano отправляет команды через него.
Один перезапуск из панели — и узел снова владеет процессом полностью.

**Подхваченный сервер, который умер, автоматически не перезапускается**, что бы ни было отмечено в
*перезапуске после падения*. Демон не запускал этот процесс, поэтому не может отличить падение от
того, что оператор остановил сервер руками на машине, — а поднять обратно сервер, который выключили
намеренно, из двух ошибок худшая.

> Чтобы демон останавливал свои серверы при выходе, как было раньше, поставьте
> `node.stop-servers-on-exit = true` в [`config.conf`](#config-conf). По умолчанию — `false`.

## Обновление демона

Раньше узел оставался на том демоне, с которым его установили, пока кто-нибудь не заходил на машину
и не менял jar руками. Теперь это не нужно: Pano отдаёт [своего собственного демона](#где-его-взять),
поэтому обновление узла — одна кнопка.

**Панель → Серверы → Узлы** помечает значком **Доступно обновление** тот узел, на котором стоит не
тот демон, какого дала бы ему эта Pano, а действие рядом обновляет этот узел на месте. Нужно право
**Управление узлами**; под капотом это `POST /api/panel/nodes/:id/update`.

Как решается, «тот демон или не тот», зависит от того, что за сборки с обеих сторон:

- **Выпущенные сборки** сравниваются по **версии**: каждый релиз Pano несёт своего демона, и Pano
  держит свою копию на этом релизе — при запуске она скачивает `pano-node.jar` своего релиза, если
  копии нет или она от другой версии (например, сразу после самообновления Pano). Так что они
  движутся вместе, и строк версий достаточно.
- **Сборки для разработки** обе вечно называют себя `local-build` и при этом пересобираются по
  несколько раз в час. Там ответ даёт **SHA-256**, который узел сообщает при подключении, против
  контрольной суммы того jar, который Pano отдаёт прямо сейчас.
- **Неизвестно — это никогда не «да».** Узел, не сообщивший версию, или Pano, которой нечего отдать,
  значка не получают: предложить обновление, которое невозможно доставить, хуже, чем не предлагать
  его вовсе.

По нажатию Pano сначала проверяет, не выполняет ли этот узел уже ровно те же байты, и если да —
отвечает `upToDate: true`. Это не формальность: отправить обновление всё равно означало бы заставить
демона скачать тот самый jar, из которого он запущен, положить его поверх себя и перезапуститься —
минута простоя для каждого сервера на этом узле ради возврата туда же, откуда всё началось. Иначе
Pano шлёт `SELF_UPDATE` с версией, контрольной суммой и **относительным** адресом jar, который узел
разворачивает относительно того адреса, по которому он уже подключён. Дальше демон

1. скачивает jar, сообщая о ходе работы в панель как о задаче `SELF_UPDATE`,
2. **проверяет SHA-256** и то, что пришёл вообще jar, — это единственное место, где демон скачивает
   код и затем выполняет его от своего имени, поэтому при несовпадении файл удаляется, а задача
   помечается неуспешной, и ничего не устанавливается,
3. кладёт файл в `<каталог-данных>/updates/` вместе с записью о том, что именно ждёт своей очереди,
4. останавливается, **на выходе кладёт подготовленный jar поверх своего** и выходит с кодом **75**.

Код выхода 75 означает «я подготовил обновление самого себя, запусти меня снова» — см.
[Коды выхода](#коды-выхода). Перезапускает демона то, что за ним следит: systemd-юнит, который пишет
[скрипт установки](../#удаленные-узлы), содержит и `SuccessExitStatus=75`, и `Restart=always`;
контейнеру нужна политика перезапуска (`--restart unless-stopped` или собственная политика Coolify);
а надзиратель Pano за локальным узлом и так считает это перезапуском. Поскольку подмена происходит
на выходе, **хватает одного перезапуска**: процесс, который запустят следующим, — это уже новый jar.
По локальным замерам узел недоступен около **трёх секунд**.

Подмена, которая не прошла, оставляет подготовленный jar и запись о нём в
`<каталог-данных>/updates/`, и демон повторяет попытку при следующем запуске, ничего не скачивая
второй раз; удачная повторная попытка снова выходит с 75 — ради ещё одного перезапуска. Если
перезапускать демона некому, узел просто останется выключенным, а обновление — ждать своей очереди.

Обновление — это перезапуск демона, но **не серверов**, за которыми он следит: они продолжают
работать всё это время и снова [подхватываются](#что-переживает-перезапуск-демона), когда демон
возвращается, так что никого не отключает и ни один мир ради этого не сохраняется и не грузится
заново. Офлайн на эти несколько секунд уходит узел, а не игра. Единственное, что сервер замечает
потом, — ввод команд в консоли: у демона нет канала в процесс, который он не запускал, и до
следующего перезапуска этого сервера из панели это берёт на себя плагин Pano.

**В Windows** jar, из которого запущен процесс, заблокирован, поэтому подмена не проходит ни на
выходе, ни при повторной попытке. Демон сообщает, где лежит новый jar, и вы копируете его поверх
старого сами — см. [Linux, macOS и Windows](#linux-macos-и-windows).

## Удаление узла {#removing-a-node}

**Удаление узла удаляет всё, что на нём есть.** **Панель → Серверы → Узлы → Удалить** (или кнопка
**Удалить этот узел?** на странице самого узла) требует права **Управление узлами**, имени узла,
набранного вручную, и пароля от аккаунта; под капотом это `POST /api/panel/nodes/:id/delete`. Перед
подтверждением окно перечисляет, что уйдёт вместе с узлом: каждый сервер на нём, сколько у них
резервных копий и сколько места они занимают, а также среды Java, которые туда скачал Pano.

Если узел **в сети**, Pano просит демона удалить себя и ждёт его — до двух минут, ход работы виден
в окне. Демон

1. останавливает каждый сервер на узле так же, как при удалении сервера (сначала мягко, затем
   завершением процесса, затем принудительно), и останавливает расписания, резервное копирование и
   передачи;
2. удаляет `servers/`, `backups/`, `java/`, `tools/`, `cache/`, свои журналы и рабочие файлы, оставляя только
   файл-метку `<data>/.pano-node-retired`;
3. удаляет свою службу, где может: юнит, записанный `--service install`, или — если он запущен от
   root — systemd-юнит `pano-node` и `/opt/pano-node`, созданные
   [скриптом установки](../#удаленные-узлы);
4. сообщает результат, отключается, удаляет `config.conf` и всё остальное в каталоге данных, что
   может, и завершается с кодом [**78**](#коды-выхода).

Затем Pano удаляет из базы данных все серверы этого узла — каждый попадает в журнал активности, как
при обычном удалении сервера, — а также токен узла, записи о резервных копиях, задачи, оповещения и,
наконец, сам узел.

**Что остаётся сделать вручную.** Всё, что демон не смог удалить сам, возвращается коротким списком
команд под заголовком **Завершите удаление на машине**, с кнопкой копирования. Список зависит от того,
как узел был установлен:

| Способ установки | Что выполнить после |
| --- | --- |
| `install.sh` от root | Обычно ничего: демон сам отключает и удаляет свой юнит. Если не смог — `sudo systemctl disable --now pano-node`, `sudo rm -rf /etc/systemd/system/pano-node.service /etc/pano-node /opt/pano-node /var/lib/pano-node`, `sudo systemctl daemon-reload` и `sudo userdel pano-node`. |
| `install.sh --user-install` | `rm -rf ~/.pano-node` |
| `--service install` (Linux) | `systemctl disable --now pano-node`, удаление скопированного юнита, затем каталог данных. |
| `--service install` (macOS) | `launchctl unload` и удаление `~/Library/LaunchAgents/com.panomc.node.plist`, затем каталог данных. |
| Установщик или служба Windows | `sc.exe stop PanoNode`, `sc.exe delete PanoNode`, затем `Remove-Item` для его папок. |
| Coolify или другой контейнер | Удалите приложение pano-node в Coolify **вместе с его постоянным хранилищем** либо `docker rm -f` для контейнера и `docker volume rm` для тома. |
| Запущен вручную | `rm -rf` для каталога данных. Jar-файл только упоминается: удалите его сами, если с него не запущен другой узел. |

**Метка «узел выведен из работы».** Демон, запущенный на каталоге данных с файлом
`.pano-node-retired`, пишет `This node was removed from Pano; nothing to do` и сразу завершается с
кодом 78: он не проходит сопряжение заново и не переподключается в цикле. Юниты systemd, которые
пишет Pano, содержат `RestartPreventExitStatus=78`, так что systemd тоже перестаёт его перезапускать.
Прежде чем снова использовать эту машину как узел, удалите каталог (или хотя бы метку).

**Узел не в сети.** Неподключённый узел ничего удалить не может, поэтому Pano отказывает с
`NODE_OFFLINE`, а окно пишет *Узел не в сети — Pano может только забыть его; файлы останутся на
машине*. Отметьте **Всё равно удалить из Pano**, чтобы удалить его несмотря на это (`force: true`):
серверы и узел исчезают из панели, на машине ничего не удаляется, а окно показывает шаги, которые
Pano может вывести из способа установки узла, — включая удаление каталога данных. Тот же выбор
появляется, когда само удаление на узле не удалось (`NODE_UNINSTALL_FAILED`, с собственной ошибкой
узла) или когда демон слишком старый, чтобы удалить себя, — чтобы удалить узел чисто, сначала
обновите его.

**Локальный узел** удаляется так же, только Pano сначала перестаёт за ним присматривать — чтобы
выход не запустил его снова, — а затем сам удаляет его каталог `node-data`. Узел возвращается в
состояние *не настроен*, и **Добавить узел → Локальный** настраивает новый.

## Коды выхода

| Код | |
| --- | --- |
| **0** | Штатное завершение. С ним же заканчиваются `--help` и `--service install` / `--service uninstall`. |
| **1** | Не удалось сопрячься: нет адреса Pano, нет кода сопряжения или стартового токена — либо Pano отвергла сопряжение. |
| **2** | Командная строка неверна — демон печатает справку. Также `--service install`, когда демон запущен не из jar. |
| **75** | **«Я подготовил обновление самого себя, запусти меня снова»** — это не сбой. |
| **76** | **Этот каталог данных занят другим демоном** — тоже не сбой, и перезапускать нечего: узел — это тот, который работает. |
| **78** | **Этот узел удалён из Pano** — он удалил себя сам или нашёл при запуске метку `.pano-node-retired`. Никогда не перезапускайте его. См. [Удаление узла](#removing-a-node). |

`75` — тот код, который важен для того, кто следит за демоном. Новый jar скачивается и проверяется в
`<каталог-данных>/updates/`, пока узел ещё работает, а поверх того jar, из которого демон запущен,
кладётся **на выходе** — когда всё уже остановлено и процесс вот-вот завершится. Поэтому запущенный
следующим процесс — это уже новый демон, и одного перезапуска достаточно. Отсюда и всё остальное:

- systemd-юнит, записанный через `--service install`, содержит `SuccessExitStatus=75`,
- юнит, который записывает [скрипт установки](../#удаленные-узлы), содержит его тоже,
- собственный надзиратель Pano за локальным узлом считает это перезапуском,
- самодельная обёртка или политика перезапуска контейнера должны просто запустить процесс снова.

Политика `Restart=always` тоже подходит: демон и так должен сразу вернуться. Подмену, которая не
прошла, демон повторяет при следующем запуске, и удачная повторная попытка снова выходит с 75 ради
ещё одного перезапуска; в Windows jar остаётся заблокированным в обоих случаях, и файл копируете
руками вы.

`78` — противоположность 75: узел [удалён](#removing-a-node) и должен оставаться остановленным.
Юниты, которые пишет Pano, содержат `RestartPreventExitStatus=78`, надзиратель Pano для локального
узла никогда его не перезапускает, и самописная обёртка или политика перезапуска контейнера тоже
должны считать этот код окончательным. Эти юниты также перечисляют его в
`SuccessExitStatus=75 78 143` рядом с `143` (JVM завершается по SIGTERM от `systemctl stop`), так
что ни удаление, ни остановка не показывают юнит как упавший (failed).

`76` не требует от надзирателя ничего: демон увидел, что блокировку его каталога данных держит
другой демон, сказал об этом и остановился — это правильный исход, а не повод запускать его снова.
См. [Каталог данных](#каталог-данных).

## Служебные файлы

`--service install` **записывает** файл юнита в `<каталог-данных>/service/` и печатает ту
единственную команду, которая его активирует. Саму команду он не выполняет никогда: регистрация
службы во всех трёх операционных системах требует root, а процесс, смысл которого — запускаться в
контейнере от непривилегированного пользователя, не должен ни тихо повышать права, ни отказываться
работать из-за того, что не смог.

| Система | Файл | Как активировать |
| --- | --- | --- |
| Linux | `pano-node.service` | Скопируйте в `/etc/systemd/system` и выполните `systemctl enable --now pano-node` |
| macOS | `com.panomc.node.plist` | Скопируйте в `~/Library/LaunchAgents` и выполните `launchctl load com.panomc.node.plist` |
| Windows | `pano-node-service.cmd` | Запустите из консоли с правами администратора — он регистрирует службу через `sc create` |

`--service uninstall` удаляет файл и печатает соответствующую команду `systemctl disable --now
pano-node`, `launchctl unload` или `sc delete PanoNode`.

## Linux, macOS и Windows

Jar переносим, и демон поддерживается на **Linux, macOS и Windows**, на x64 и arm64 (arm32 — по
возможности). Различия изолированы, но о них стоит знать:

- **Остановка сервера.** В Windows нет сигнала, который вежливо просит процесс завершиться, поэтому
  последовательность там такая: собственная команда остановки сервера, затем завершение, затем
  убийство — те же три шага, которые показывает Pano, только средний делает меньше, чем на Linux и
  macOS. Дайте большому миру чуть больше времени на сохранение.
- **Регистрация службы** отличается, как описано выше; в Windows нет файла юнита, есть только
  скрипт, вызывающий `sc create`.
- **Самообновление.** Windows блокирует jar, из которого запущен процесс, поэтому подмена там не
  удаётся, и демон сообщает, где лежит новый jar: **скопируйте его поверх старого и запустите службу
  заново**. На Linux и macOS подмена происходит сама. Установщик, который решает это на Windows,
  запланирован.
- **Пути и права** обрабатываются отдельно для каждой системы; права «только владелец» на
  `config.conf` ставятся там, где файловая система их поддерживает.

## Безопасность

- **Только исходящие соединения.** Соединение к Pano открывает и держит демон; Pano к узлу не
  подключается никогда, и **открывать порты на узле не нужно**. Это работает за NAT и за
  брандмауэром, который не пропускает внутрь ничего.
- **С аутентификацией и шифрованием.** При сопряжении ключ AES-256 передаётся завёрнутым в
  собственный открытый ключ RSA узла, по тому адресу, который вы указали, — для узла не на той же
  машине используйте **HTTPS**. Дальше WebSocket несёт токен JWT, а каждый кадр в нём зашифрован
  **AES-256-GCM**, ровно как в соединении плагина Minecraft.
- **Код сопряжения живёт недолго.** Шесть цифр, смена каждые 30 секунд, и узел, сопряжённый по
  такому коду, **не считается доверенным, пока администратор не примет его** в панели. Принимайте
  только те машины, которые настроили сами.
- **Файловая система в песочнице.** Каждый путь, который присылает Pano, нормализуется и проверяется
  на принадлежность каталогу именно этого сервера; `..`, абсолютные пути и символические ссылки
  наружу отвергаются, а чёрный список не пускает панель к файлам с учётными данными — в их числе
  собственный `config.conf` плагина Pano.
- **Никакой оболочки.** Серверы запускаются списком аргументов, а не через shell, поэтому ничто в
  имени, флаге или пути не может стать второй командой. Демон ещё и вычищает из наследуемого
  сервером окружения `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS`, `JDK_JAVA_OPTIONS` и `CLASSPATH`, чтобы
  флаги, предназначенные ему самому, не доходили до игры.
- **Он не повышает права.** Демон работает от того пользователя, который его запустил, и пишет
  только внутрь своего каталога данных.
